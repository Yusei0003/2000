## 1. アーキテクチャ概要

### 1.1 全体構成

サーバーを持たない、ブラウザ単体で完結する静的Webアプリケーション。ビルド工程を持たず、`index.html` をブラウザで開くだけで動作する（`file://` での直接オープン、または `python3 -m http.server` 等での配信のいずれにも対応）。

```
index.html  … 画面の骨格（タブ・カード・フォーム・テーブルの雛形）とスクリプト読込
style.css   … 全画面共通のスタイル
app.js      … 純粋なロジック層（日付計算・祝日判定・割当アルゴリズム・OCR解析等）
ui.js       … 画面制御層（DOM操作・イベント処理・データの読み書き・Excel入出力）
docs-content.js … 仕様書・設計書のMarkdown本文を文字列として埋め込んだファイル（第7章）
vendor/     … 同梱ライブラリ一式（外部通信なし）
docs/       … 仕様書・設計書のMarkdown原本（アプリ内表示用文字列の生成元）
```

`app.js` を先に読み込み、`ui.js` が `app.js` の関数をグローバル関数として直接呼び出す（ES Modules は使用せず、`<script>` の読込順のみに依存する）。Node.js からは `module.exports`（`app.js` 末尾）経由でユニットテスト用に読み込める。

### 1.2 設計方針

| 方針 | 理由 |
| --- | --- |
| ビルド工程なし | 庁内PCでの配置・更新を、ファイルの上書きだけで完結させるため |
| 外部通信なし | ネットワーク接続のない端末で動作させるため。ライブラリは全て `vendor/` に同梱 |
| ロジックとUIの分離 | `app.js`（純粋関数、日付・文字列・オブジェクトのみを扱う）をNode.js上でユニットテスト可能にするため |
| localStorageのみ | サーバー・DBを持たないため。バックアップ（JSON書出）で永続化の弱さを補う |
| 段階的マイグレーション | データ構造を変更した際、起動時に一度だけ自動移行する関数を都度追加し、既存データを破壊しない |

## 2. 画面構成・コンポーネント設計

### 2.1 タブ構成

`index.html` は `<nav class="tabs">` に並ぶボタン（`data-tab` 属性）と、対応する `<section id="panel-xxx" class="tab-panel">` の組で構成される。`initTabs()`（ui.js）がクリックで表示切替を行う。

| data-tab | パネルID | 内容 |
| --- | --- | --- |
| staff | panel-staff | 名簿管理 |
| rules | panel-rules | ルール設定 |
| events | panel-events | 行事管理 |
| generate | panel-generate | 勤務表作成 |
| history | panel-history | 履歴・確認 |
| help | panel-help | 使い方 |
| docs | panel-docs | 仕様書・設計書（第7章） |

各タブの下は複数の `.card` に分かれ、`.card` 単位で機能がまとまる（例：名簿管理タブは「1. Excel名簿データの取り込み」「2. 職員名簿」「3. 職員を追加」の3カード）。

### 2.2 画面共通部品

| 部品 | 内容 |
| --- | --- |
| `.period-bar` | 画面最上部に常時表示される処理期セレクタ・処理期の追加/コピー/削除ボタン |
| `.table-wrap` | テーブルをスクロール可能にするラッパー。`thead` に `position: sticky` を適用しヘッダー行を固定 |
| `.modal-root` | 変更届反映モーダル（`openChangeModal`）等の差し込み先 |
| `#toast` | 操作結果を通知するトースト（`showToast()`） |
| `.assign-name-chip` | 勤務表作成結果一覧の、ドラッグ入れ替え可能な職員名の札 |

### 2.3 レンダリング方式

Reactのような仮想DOMは使わず、各 `render*()` 関数が対象要素の `innerHTML` を文字列テンプレートで丸ごと再構築する素朴な方式。データが変わるたびに該当する `render*()` を呼び直す（例：`renderStaffTable()`、`renderGenResultTable()`）。イベントリスナーは再描画のたびに `querySelectorAll` で拾い直して付け替える。

### 3.3 IDの一貫性設計

名簿を処理期ごとに独立して保持する一方、確定済み履歴・120日間隔・ペア重複回避は処理期をまたいで同一人物を追跡する必要がある。これを両立させるため、**職員番号を恒久キーとして職員IDを固定化**している（`duty_staff_id_map_v1`）。

- `idForNumber(number)`：番号に対応するIDが未発行なら新規発行し、以後は同じ番号に対して常に同じIDを返す
- Excel名簿取込・CSV取込・個別登録のいずれも、新規レコードのIDはこの関数経由で発行する
- 結果として、同じ職員が複数の処理期の名簿に登場しても（別のオブジェクトインスタンスとして）同じ `id` を持ち、履歴のIDと照合できる

処理期をまたいだ表示名解決（履歴・確認タブ、引継ぎ用Excel等）には `resolveAnyStaff(id)` を使う。これは「現在の処理期の名簿」→「全処理期の名簿」→「履歴専用スタブ」の順にIDを検索する。一方、名簿管理タブや勤務表作成タブでの選択肢構築には `staffById(id)`（現在の処理期の名簿のみを検索）を使う。両者を使い分けることで、「編集対象は必ず現在の処理期の職員」「表示専用の名前解決はどの処理期の職員でもよい」という意味の違いを型レベルではなくコーディング規約で表現している。

## 4. 主要モジュール設計（app.js）

`app.js` は副作用を持たない純粋関数の集合。DOM・localStorageへの参照を持たない。

### 4.1 機能グループ

| グループ | 主な関数 |
| --- | --- |
| 日付ユーティリティ | `toISO` `parseISO` `addDays` `diffDays` `addMonths` `fiscalYearOf` |
| 祝日計算 | `holidayMapOfYear` `isJapaneseHoliday`（ハッピーマンデー・振替休日・国民の休日を含む近似式） |
| 指定日抽出 | `listDesignatedDates` `isYearEndClosure` |
| 特別期間判定 | `detectSpecialPeriod` `previousSpecialKeys`（年末年始・GW） |
| 資格・除外判定 | `effectiveCitizenExp` `isQualified` `isStandingExcluded` `standingExcludedReason` `isOnLeave` |
| 処理期計算 | `periodIdOf` `periodRange` `periodLabelOf` `previousPeriodOf` `periodOfDate` |
| 割当アルゴリズム | `generateAssignments`（第5章） |
| 未割当理由の説明 | `explainUnassignedStaff` |
| テキスト解析（OCR・貼り付け共通） | `extractLabelValue` `parseOcrDateTime` `parseOcrDate` `levenshtein` `bestNameMatch` |

### 4.2 純粋関数として設計する理由

割当アルゴリズムはルールの数が多く（第8章参照）、組合せの妥当性をユニットテストで機械的に検証する必要がある。DOM・localStorageに依存しない純粋関数にすることで、Node.js上で `require('./app.js')` するだけで、実データを模したオブジェクトを渡す形のテストが書ける（第9章）。

### 4.3 変更届の反映（`openChangeModal` / `applyChangeDraftFromText`）

変更届の内容（交代相手氏名・申請日時・変更する日付・申請者）をテキストから読み取る処理は、入力元がOCR結果でもグループウェア等からの直接貼り付けでも**まったく同じロジック**を通す。`applyChangeDraftFromText(text, targetDate, candidates, currentName)`（ui.js）が唯一の実装で、`extractLabelValue()`（app.js）で各ラベルの値を取り出し、`bestNameMatch()` で氏名を名簿の職員へファジーマッチし、`parseOcrDateTime()` / `parseOcrDate()` で日付を解釈する。

- `runChangeOcr(file, targetDate, candidates, currentName)`：Tesseract.js でスクリーンショットをOCRし、結果のテキストを `applyChangeDraftFromText` に渡す。`file://` では Tesseract のワーカー読込がブラウザの制約で失敗するため使用できない
- `runChangeTextPaste(text, targetDate, candidates, currentName, statusEl)`：テキストエリアの内容（貼り付け時に自動実行、またはボタンで手動実行）をそのまま `applyChangeDraftFromText` に渡す。画像認識を経由しないため `file://` でも制約なく動作する

`applyChangeDraftFromText` は、読み取った「変更する日付」がモーダルの対象日と異なる場合、および読み取った「申請者」がその日の現在の担当者（`currentName`）と異なる場合に、それぞれ警告メッセージを返す。誤って別の変更届の内容を読み込んでしまうミスを防ぐための照合で、値のプレフィルとは独立して常に実行される。

## 5. 割当アルゴリズム設計（generateAssignments）

詳細な業務ルールは仕様書 第8章、判定フローの図解は `docs/勤務表作成フロー.md` を参照。本章では実装上のデータフローを記す。

### 5.1 入力

```
generateAssignments({
  staffList, dutyDates, monthRules, eventExclusions, history,
  minGapDays, newHireMonths, specialLookback, pairLookbackYears,
  standingExcludedDepts, leaves, retireLeadMonths, periodId,
})
```

`retireLeadMonths`（既定1）は `passesRetire(staff, date, retireLeadMonths)` の許容ヶ月数。育休・産休の `isOnLeave` と同じ扱いで `eligibleBase` の絶対条件に組み込まれており、5.5a節の最終手段でも緩和しない（`staff.retireDate` が未設定の職員は常に true を返す）。

`periodId` を渡すと同一処理期内1人1回ルールが有効になる（未指定時は無効。ユニットテストで1人1回ルールを検証しない場合に使う）。

`eventExclusions` の各要素は `{ date, endDate, depts, targetElectionDuty }` の形（ui.jsの`computeEventExclusions()`が組み立てる）。日ごとのループでは、`date`〜`endDate` の範囲に入る行事について `depts` を `excludedDepts`（Set）へ合流させるのに加え、`targetElectionDuty` が true の行事が1つでもあればその日のフラグ `electionDutyExcludedToday` を立てる。`eligibleBase(level, gender, ignoreGap, ignoreElectionDuty)` の第4引数が false の間はこのフラグと `staff.electionDuty` の両方が真の職員を除外する（`ignoreElectionDuty || !(electionDutyExcludedToday && s.electionDuty)`）。選挙管理委員会事務局は名簿上の所属として存在しない（併任のため）ため、既存の所属ベースの除外（`depts`）では対象を特定できない。個人単位のフラグを別軸として持つことで、所属ベースの除外とは独立に併任者だけを選挙の告示日前後で除外できるようにしている。所属ベースの除外（`excludedDepts`）は常に緩和しない絶対条件のままだが、選挙管理委員会（併任）の除外だけは、他の候補で2名の枠を埋められない場合に限り `searchGenderFull` の最終手段で緩和する（5.5a節、1.14節）。

### 5.2 前処理で構築するマップ

| マップ | キー | 用途 |
| --- | --- | --- |
| `countMap` | 職員ID | 累計担当回数（候補の並び替えに使用） |
| `lastDateMap` | 職員ID | 前回勤務日（120日間隔の判定） |
| `specialUse` | 特別期間キー | その期間の担当者集合（年末年始/GW重複回避） |
| `pairLastFY` | ペアキー（第5.4節） | 組んだ最後の年度（ペア重複回避） |
| `periodUsedIds` | — | 選択中の処理期で既に使われた職員IDの集合（1人1回ルール） |

日ごとのループの外側には、上記のマップに加えて `genderZone`（`'F'` / `'M'`）と `femaleUsedThisPeriod`（真偽値）という2つの状態変数を持つ（性別ゾーン、5.4a/5.4b節）。

### 5.3 日ごとのループ（`sorted.forEach`）

指定日を日付の昇順でソートし、1日ずつ処理する。前の日の結果は `countMap` `lastDateMap` `periodUsedIds` 等に反映されるため、次の日の判定に影響する（＝日付順の処理順序に結果が依存する）。

各日の処理は `eligibleBase(level, gender)` で「その日・その級・その性別」の候補配列を作るところから始まる（除外条件は仕様書 8.3節）。

### 5.4 ペア決定ロジック（`tryGender` / `findPair`）

1日2名のうち少なくとも1名が係長級であればよいというルールを、以下のプール構成で実現している。

```
seniorPool   = eligibleBase('senior', gender) を並び替えたもの（1人目候補。必ず係長級）
juniorPool   = eligibleBase('junior', gender) を並び替えたもの
combinedPool = seniorPool と juniorPool を interleave（交互配置）してから
               並び替えたもの（2人目候補。係長級・主事級を問わない）
```

`interleave` を挟むのは、`sortByCountAndRecency`（担当回数→前回勤務日のみで比較し、資格要件による優先を含まない並び替え）が同点（担当回数・前回勤務日とも未設定）のときに配列の並び順を保持する安定ソートであるため、単純結合すると同点集団の中で係長級が常に先頭に来てしまい、「係長級2名」と「係長級＋主事級」が対等に扱われなくなる（詳細は5.6節）。これを避けるため、事前に交互配置してから並び替える。

`findPair(seniorPool, partnerPool, opts)` は `seniorPool` の先頭から1名（anchor）、`partnerPool` の先頭から自分自身以外の1名（partner）を選ぶ総当たりで、`opts` に応じて以下を判定する。

| opts | 判定内容 |
| --- | --- |
| `avoidSameDept` | anchorとpartnerの所属が同じでないか |
| `avoidPairRepeat` | `isPairBanned()`（過去N年度以内に組んでいないか） |
| `avoidTitleClash` | partnerも係長級の場合、`isSeniorTitleClash()`（課長補佐/副主幹の組合せでないか） |
| `requireQualification` | `isQualified(anchor) \|\| isQualified(partner)`（anchorは常に係長級＝常に true） |

`tryGender(gender)` は、`stages`（5段階、5.5節）を先頭から順に試し、最初に見つかったペアを採用する。同一処理期内はまず `periodUsedIds` を除いた「今期未割当」プールのみで探索し、1人目プールが空になった場合に限り、`periodUsedIds` を含めた全候補で再探索する（この再探索で見つかったペアは `repeat: true` を返す）。

`allowRepeat=false` のときだけ `periodUsedIds`（今期割当済み）を除外したプールで探索する。性別と1人1回のどちらを優先するかは `tryGender` の内部では決めず、呼び出し側（5.4a節の性別ゾーン制御）が明示的に順序を組み立てる。

当初は `tryGender` の内部で「今期未割当が枯渇したら即座に今期2回目へ」とエスカレートしていたため、`tryGender('F')` が常にペアを返してしまい **男性の1回目が一度も試されない**という不具合があった（女性が少ない職場で、男性が未割当のまま女性が2回目に回る）。この責務を `tryGender` から呼び出し側へ移し、性別と1人1回の優先順位を明示的に制御するようにして解消した。

### 5.4a 性別ゾーン（`genderZone` / `zoneToday` / `searchGenderFull`）

「男性の期間の途中に女性が単発で混ざると担当交代がしづらい」という運用上の要請を満たすため、`generateAssignments` は日ごとのループの外側に `genderZone`（`'F'` または `'M'`。一度 `'M'` になったら二度と `'F'` に戻らない）と `femaleUsedThisPeriod`（安全弁。5.4b節）という2つの状態を持つ。

```js
let zoneToday = genderZone;
let outcome;
if (zoneToday === 'F') {
  const freshF = tryGender('F', false);
  if (freshF.pair) {
    outcome = freshF;
  } else {
    const maleFull = searchGenderFull('M', true); // 未割当→2回目→最終手段まで男性だけで探す
    if (maleFull.pair) {
      zoneToday = 'M';
      outcome = maleFull;
    } else {
      outcome = searchGenderFull('F', false); // 男性が皆無なら女性側の2回目・最終手段に留まる
    }
  }
} else {
  outcome = searchGenderFull('M', true);
}
```

`searchGenderFull(gender, includeFresh)` は、指定した性別だけに固定して「（includeFreshなら）今期未割当 → 今期2回目 → 最終手段（係長級の有無・120日ルールを緩和した、旧5.5a節相当の同性版）」まで一気通貫で探す関数で、5.4b節の最終手段ロジックをこの関数の中に統合している。**他方の性別へは一切広げない**のが5.5a節（旧版）からの最大の変更点である。

ポイントは以下の3点。

1. 女性ゾーン（`zoneToday === 'F'`）では、まず `tryGender('F', false)`（女性・今期未割当）**のみ**を試す。ここで女性の「2回目」を試してしまうと、女性が少数でも repeat だけで無限に粘ってしまい、男性が一度も使われなくなるため、あえて未割当のみに限定している。
2. ①が失敗した日に限り、`searchGenderFull('M', true)` で男性を（未割当→2回目→最終手段まで）フルに探す。ここで見つかれば（1名のみの最終手段でも）その日から `zoneToday = 'M'` とし、以後 `genderZone` もラッチする。
3. ②もまったく見つからない場合（＝そもそも男性が0名、または全員が対象外）は、ゾーンを切り替えても意味がないため `searchGenderFull('F', false)` で女性側の2回目・最終手段を試す。この場合 `zoneToday` は `'F'` のままで、ラッチも発生しない（全員女性の職場でも欠員を作らないための保険）。

`genderZone` のラッチは次の1行で行う。

```js
if (usedGenderToday === 'F') femaleUsedThisPeriod = true;
if (zoneToday === 'M' && femaleUsedThisPeriod) genderZone = 'M';
```

### 5.4b 安全弁と処理期をまたいだゾーンの復元

`femaleUsedThisPeriod` が `false` のまま（＝この処理期でまだ一度も女性を使っていない）男性が使われた日があっても、その1日だけでは `genderZone` をラッチしない。行事除外等で処理期の冒頭にたまたま1日だけ女性が0人になっても、翌日以降は通常どおり女性ゾーンから再開する（女性ゾーンが実質的に始まる前の誤確定を防ぐ安全弁）。

処理期を分けて（例：前半・後半）生成する運用に対応するため、`periodId` が指定されている場合は、その処理期の確定済み履歴を日付順に読み直して `genderZone` / `femaleUsedThisPeriod` の初期値を復元する。

```js
const staffGenderById = new Map(staffList.map((s) => [s.id, s.gender]));
history
  .filter((h) => h.periodId === periodId)
  .sort((a, b) => (a.date < b.date ? -1 : a.date > b.date ? 1 : 0))
  .forEach((h) => {
    const genders = [h.seniorId, h.juniorId].filter(Boolean).map((id) => staffGenderById.get(id)).filter(Boolean);
    if (genders.includes('F')) femaleUsedThisPeriod = true;
    if (genders.length > 0 && genders.every((g) => g === 'M') && femaleUsedThisPeriod) genderZone = 'M';
  });
```

履歴に性別は保存されていないため、`staffList`（現在の処理期の名簿）から都度引く。名簿は処理期ごとに保持しており、その処理期に確定した履歴の対象者は同じ処理期の名簿に必ず存在するという前提に依っている。

### 5.5 段階的緩和（stages配列）

```js
const stages = [
  { avoidSameDept: true,  avoidPairRepeat: true,  avoidTitleClash: true,  requireQualification: true },  // 第1段階
  { avoidSameDept: true,  avoidPairRepeat: false, avoidTitleClash: true,  requireQualification: true },  // 第2段階
  { avoidSameDept: true,  avoidPairRepeat: false, avoidTitleClash: false, requireQualification: true },  // 第3段階
  { avoidSameDept: false, avoidPairRepeat: false, avoidTitleClash: false, requireQualification: true },  // 第4段階
  { avoidSameDept: false, avoidPairRepeat: false, avoidTitleClash: false, requireQualification: false }, // 第5段階
];
```

いずれの段階でもペアが見つからない場合、1人目プールが1名以上いれば「1人目の先頭候補＋2人目プールの先頭候補（1人目と別人）」を無条件で採用する（最終手段。`relaxedStage = stages.length` として扱う）。

`relaxedStage` の値と `repeat` フラグから、`reasons`（要確認理由の配列）を組み立てる（仕様書 8.3節の理由文言に対応）。

### 5.5a 人数不足時の最終手段（`searchGenderFull` 内・性別はゾーンに固定）

`searchGenderFull(gender, includeFresh)`（5.4a節）は、通常探索（今期未割当→今期2回目）が尽きたあと、指定された **その性別のまま** さらに一段階緩い最終手段を実行する。旧版（〜1.2）はここで性別を問わない候補プール（`eligibleBase(level, null)`）を使っていたが、現在は必ず `eligibleBase(level, gender)` と**性別を固定**する。

緩和の軸は `ignoreGap`（最低間隔日数）・`ignoreElectionDuty`（選挙管理委員会（併任）の除外、1.14節）の2つがあり、緩和が少ない順に4通り（`{false,false}` → `{true,false}` → `{false,true}` → `{true,true}`）を試す。

```js
const combos = [
  { ignoreGap: false, ignoreElectionDuty: false },
  { ignoreGap: true, ignoreElectionDuty: false },
  { ignoreGap: false, ignoreElectionDuty: true },
  { ignoreGap: true, ignoreElectionDuty: true },
];
let soloCandidate = null; // 2名の組合せが1つも見つからなかった場合の最終フォールバック
for (const { ignoreGap, ignoreElectionDuty } of combos) {
  if (pair) break;
  const zSeniorPool = sortCandidates(eligibleBase('senior', gender, ignoreGap, ignoreElectionDuty), countMap, lastDateMap);
  const zCombinedPool = sortByCountAndRecency(interleave(zSeniorPool, zJuniorPool), countMap, lastDateMap);
  if (zSeniorPool.length) {
    // 係長級がいて、かつ相方も見つかれば確定。相方がいなければ soloCandidate として記憶するだけで、
    // ここでは pair を確定しない（より緩和すれば2名の組合せが作れる可能性を残すため）。
  } else if (zCombinedPool.length >= 2) {
    // 係長級が1名もいない場合、担当回数の少ない同性2名を機械的に組む（forcedNoSenior）。ここは即確定。
  } else if (zCombinedPool.length === 1 && !soloCandidate) {
    // 対象者が1名のみ：soloCandidateとして記憶するだけで、まだ確定しない
  }
}
if (!pair && soloCandidate) {
  // 4通りすべてで2名の組合せが作れなかった場合にのみ、最初に見つかった（＝最も緩和の少ない）
  // soloCandidateを採用する（片方は null のまま）
}
```

1つ目の軸（`ignoreGap`）は最低間隔日数（`minGapDays`、既定120日）を守ったまま探し、それでも対象者が1名も残らない場合に限り `passesGap` の判定を外して探す。処理期の後半では全職員が「前回勤務日から120日以内」に該当しうるため、これがないと**在籍者がいるのに誰も割り当てられない日**が発生する。`ignoreGap: true` で割り当てた場合は `forcedIgnoredGap` を立て、理由に「前回勤務日から120日未満の職員を含みます（人数不足のため）」を表示する。

2つ目の軸（`ignoreElectionDuty`）は、選挙管理委員会併任者を対象にした行事の除外期間中に、他の候補で2名の枠を埋められない場合に限り、その除外を緩和する（1.14節で追加）。`ignoreElectionDuty: true` で割り当てた場合は `forcedElectionDutyUsed` を立て、理由に「選挙管理委員会事務局（併任）の職員を人数不足のため特例的に割り当てました」を表示する。

**「1名のみ確定してよいのは、4通りすべてを試しても2名の組合せが作れなかった場合に限る」** という判定順序が重要である。旧版（`ignoreGap` のみの1軸だった頃）は、緩和の浅い段階でたまたま `zCombinedPool.length === 1` となった時点で即座に `pair` を確定して探索を打ち切っていた。`ignoreElectionDuty` 軸を素朴に外側のループとして追加すると、この「即確定」がより緩い段階（＝2名の組合せが作れたはずの段階）を試す前に探索を止めてしまう不具合が生じる（実装中にテストで検出）。これを避けるため、`zSeniorPool.length` かつ相方なしのケースと `zCombinedPool.length === 1` のケースは即確定せず `soloCandidate` として記憶するだけにとどめ、4通りすべてのループが終わったあとで、なお `pair` が見つかっていない場合にのみ最初に記憶した `soloCandidate`（＝最も緩和が少ない段階のもの）を採用するよう変更した。

この経路で選ばれたペアは、同一課・ペア重複・課長補佐/副主幹の組合せ・資格要件のいずれのチェックも経ていない（`findPair` を使わず、`zCombinedPool` の先頭から機械的に選ぶ）。`assignedCount`（実際に割り当てられた人数、0〜2）が2未満の場合は `status = 'error'`、2名は埋まったが係長級不在等が生じた場合は `status = 'warning'` とする（「OK / 要確認 / エラー」の3値）。**性別ゾーンをまたぐ穴埋め（男性ゾーンで女性を使う等）は行わない**ため、ゾーン内の対象者が本当に尽きた場合はエラーになる。

この最終手段（`forcedFallbackUsed`）で選んだペアは、`findPair` を経由しないため通常の `repeat` 判定（`tryGender` 内）を通っていない。そのため `searchGenderFull` の末尾で、最終手段で選んだ相手が `periodUsedIds`（今期割当済み）に含まれるかを改めて判定し直し、`repeat` を上書きする。この後処理がないと、最終手段でしか埋まらない小規模な職場（在職者が少なく毎回同じ顔ぶれになる）で「同一処理期内で2回目の割当です」という理由が理由欄から欠落する不具合があった（ユニットテストで検出・修正）。

### 5.6 タイブレークの公平性（`interleave` / `sortByCountAndRecency`）

`sortCandidates`（資格要件による優先を含む、1人目プール用）と `sortByCountAndRecency`（資格要件を含まない、2人目プール用）を明確に分離している。歴史的経緯として、当初は2人目プールにも `sortCandidates` を流用していたが、係長級は `isQualified` が常に true・主事級は市民課経験がなければ false になるため、担当回数に関わらず係長級が主事級より常に先に並んでしまう不具合があった（ユニットテストで検出・修正）。「係長級2名を係長級＋主事級と対等に扱う」という要件を満たすため、2人目プールの並び替えからは資格要件由来の優先を完全に除外している。

### 5.7 ペアキーの対称性（`pairKey`）

```js
function pairKey(idA, idB) {
  return [idA, idB].sort().join('|');
}
```

係長級2名のペアでは、どちらがanchor／partnerになるかは探索順に依存し、日によって入れ替わりうる。`pairKey` を2つのIDのソート結果に基づく対称なキーにすることで、`(A, B)` と `(B, A)` を同一のペアとして扱い、ペア重複回避が anchor/partner の順序に依存しないようにしている（元は `seniorId + '|' + juniorId` という非対称なキーだったが、係長級2名ペアの導入に合わせて修正した）。

## 6. 名簿管理の設計

### 6.1 処理期ごとの名簿と移行

名簿は処理期ごとに独立して保持する（3.1節）。旧バージョン（処理期共通の1本の名簿）からの移行は `migrateToPerPeriodStaff()` が起動時に一度だけ実行する。

- 旧名簿のうち `dept` が空のレコード（勤務実績Excel取込で自動生成された履歴専用スタブ）を判別し、`duty_history_staff_v1` へ分離する
- 残りは、**移行時点で選択中の処理期のみ**に複製する（他の処理期は「未取込」のまま残し、名簿管理タブには表示しない。当時の全処理期に複製していた初期実装から、「名簿は処理期ごとに取り込む」という運用方針に合わせて変更した）
- 職員IDは旧レコードのIDをそのまま引き継ぎ、`duty_staff_id_map_v1` を構築する（履歴の整合性を保つため）

### 6.2 Excel名簿取込（置き換え方式）

「1. Excel名簿データの取り込み」を確定すると、選択中の処理期の名簿を**取込内容で全置換**する（既存レコードとの突き合わせ更新は行わない）。置換時、`previousPeriodStaffMap()`（直前の処理期の名簿を職員番号でひけるマップ）を参照し、以下を新レコードへ引き継ぐ。

| 引き継ぐ項目 | 条件 |
| --- | --- |
| `citizenExp` | 前処理期で true だった場合、または今回の所属が「市民課」を含む場合 |
| `dispatched` | 前処理期で true だった場合 |
| `seventyPercent` | 前処理期で true だった場合 |
| `deptHistory` | 前処理期の `deptHistory` を引き継ぎ、所属が変わっていれば前処理期の所属を追加 |
| `retireDate` | 今回のExcel行に退職日があればそれを優先し、無ければ前処理期の `retireDate` を引き継ぐ |

`active`（対象に含めるか）は引き継がない（Excelに再登場した時点で対象復帰とみなす）。`category` / `status` / `age`（区分名・身分・年齢）は前処理期から引き継がず、常に今回のExcel行の値をそのまま設定する（毎回のExcel出力に含まれる前提の参考情報のため）。取込結果のサマリー（引継ぎ件数の内訳）は `#staff-xlsx-summary` に表示し続ける（トーストは短時間で消えるため、確認可能な形で残す）。

**取込時の除外判定の変更点（v1.7）：** 旧版は「退職日が設定されている＝除外」だった。退職日は退職予定日として事前に人事システムへ登録されることがあるため、この判定では実際にはまだ在職中の職員まで取込対象外になってしまう。現在は `r.retireDate < 選択中の処理期のstartDate` の場合（＝処理期が始まる前に既に退職している）のみ取込対象外とし、それ以外の退職日は `retireDate` としてそのまま名簿に取り込む。取込から除外された行（区分除外・級判定不可・既に退職済みのいずれか）は理由付きで `duty_import_excluded_v1`（処理期ID単位）に保存し、「Excel取込で除外された人」CSVで確認できる（6.4節）。

### 6.3 空の名簿の扱い

`hasRosterForCurrentPeriod()` が選択中の処理期の名簿配列の有無を判定し、`renderStaffTable()` は未取込の処理期では一覧テーブル（`#staff-roster-body`）を非表示にし、案内文（`#staff-empty-period-note`）を表示する。`savePeriodStaff()` は、名簿が空になった場合（全削除等）に `periodStaff` オブジェクトから該当処理期のキー自体を削除し、「未取込」の状態に戻す。

### 6.4 除外者のCSV出力

名簿管理タブには2種類のCSV出力ボタンがある。いずれも列は「職員番号・区分名・身分・名前・所属名・職名・年齢」で、除外リストのみ末尾に「除外理由」を追加する。

| ボタン | データソース | 内容 |
| --- | --- | --- |
| Excel取込で除外された人をCSV書出 | `periodImportExcluded[currentPeriod().id]`（直近のExcel取込時に確定） | 区分による除外・級を判定できない・既に退職済みのいずれかで取込対象外になった行 |
| 除外リストの人をCSV書出 | `staff` を `renderStaffTable()` と同じ条件（`active === false \|\| isStandingExcluded()`）で絞り込んだもの | 現在の名簿の除外リストに表示されている職員（除外理由は `exclusionReason()` を再利用） |

前者は取込時のスナップショットのため、取込後に名簿を手動編集しても再取込するまでは更新されない。後者は名簿の現在の状態をそのつど反映する。

## 6a. 勤務表作成・確定フローの設計

既存の章番号を変更しないよう、5.4a節等と同じ慣例でアルファベット付きの章番号とする。

### 6a.1 課題と設計方針

旧版は「勤務表を作成する」→「この内容で確定・履歴に保存」を押すと、確定と同時に `draftDates` / `draftResults`（勤務表作成タブの作業中の状態）を即座に空へリセットしていた。これには2つの問題があった。

1. **決裁前に確定できてしまう。** 確定はワンクリックで完了し、内容を確認・決裁したことを確認する仕組みがなかった。
2. **確定後に画面が消える。** どのような設定・除外条件でその内容が作られたかを、確定後に見返す手段がなかった（`draftDates` / `draftResults` はどこにも永続化されず、画面をリロードするだけで消える一時変数だった）。

これを解消するため、勤務表作成タブの作業状態を処理期ごとに永続化し、「作成中（draft）」「決裁・確定済み（confirmed）」の2状態を持つ**確定フロー**を導入した。

### 6a.2 セッションの永続化（`genSessions` / `saveGenSession` / `loadGenSessionForCurrentPeriod`）

`draftDates` / `draftResults` に加えて、決裁・確定状態を表す変数群（`genStatus`, `genConfirmBatchId`, `genConfirmedAt`, `genApprovalChecked`, `genLog`, `genFrozenUnassignedHtml`, `genFrozenOverburdenedHtml`）をモジュール変数として持つ。これらをまとめて `duty_gen_session_v1`（`genSessions`、処理期ID→セッションオブジェクト）へ保存・復元する。

```js
function saveGenSession() {
  genSessions[currentPeriod().id] = {
    status: genStatus, dates: draftDates, results: draftResults, genDatesEmptyReason,
    approvalChecked: genApprovalChecked, confirmBatchId: genConfirmBatchId, confirmedAt: genConfirmedAt,
    log: genLog, frozenUnassignedHtml: genFrozenUnassignedHtml, frozenOverburdenedHtml: genFrozenOverburdenedHtml,
  };
  save(KEY_GEN_SESSION, genSessions);
}
```

`applyPeriodToGenerateTab()`（処理期切替時・起動時に呼ばれる）は、`draftDates` / `draftResults` を空にリセットする代わりに `loadGenSessionForCurrentPeriod()` を呼び、選択中の処理期に保存済みのセッションがあればそれを復元する（無ければ空の下書き状態から開始する）。これにより、タブを離れても、画面をリロードしても、作成時の内容がそのまま保持される。

内容を変更しうる全ての操作（自動抽出のやり直し・勤務表の再作成・プルダウン変更・ドラッグ入れ替え・指定日のチェック変更）は、直後に必ず `saveGenSession()` を呼ぶ。またこれらの操作は同時に `genApprovalChecked = false` をセットする（6a.3節）。

### 6a.3 決裁確認ゲート

確定ボタン（`#gen-confirm`）は、`draftResults` が空でないことに加えて `genApprovalChecked === true` でなければ活性化しない。チェックボックス（`#gen-approval-check`）は `genStatus === 'confirmed'` の間は操作できない。

内容を変更する操作のたびに `genApprovalChecked` を `false` に戻すのは、「決裁を得た時点の内容」と「実際に確定される内容」が食い違うことを防ぐためである。決裁後に何らかの理由で内容を1箇所でも変更した場合、チェックは自動的に外れ、確定するには再度チェックを入れ直す必要がある。

### 6a.4 確定（決裁済みロック）と `confirmBatchId`

確定操作は以下を行う。

1. その時点の `computeUnassignedSummaryHtml()` / `computeOverburdenedSummaryHtml()`（未割当職員・担当過多のサマリHTML）を `genFrozenUnassignedHtml` / `genFrozenOverburdenedHtml` に凍結保存する（6a.5節）。
2. `uid('cb')` で `confirmBatchId` を新規発行し、`draftResults` の各行に `periodId` / `periodLabel` / `confirmedAt` / `confirmBatchId` を付与して `history` へ追加する。
3. `draftResults` を（`confirmBatchId` 等が付与された）確定後の内容で置き換え、**クリアしない**。
4. `genStatus = 'confirmed'` とし、`saveGenSession()` で永続化する。

`genStatus === 'confirmed'` の間、`renderGenDatesTable()` / `renderGenResultTable()` は指定日チェックボックス・プルダウン・ドラッグ入れ替えを `disabled` / `draggable="false"` にして描画し、各操作の実処理（イベントハンドラ）側でも `if (genStatus === 'confirmed') return;` で二重に防御する。「土日・祝日・年末年始を自動抽出」「勤務表を作成する」ボタンおよび対象期間の日付入力も `disabled` にする。これにより、確定後に自動処理や誤操作で内容が変わることはない。

### 6a.5 除外対象者等の履歴の凍結（スナップショット）

「未割当職員」「担当回数が多い職員」の2つのサマリは、通常時（作成中）は `staff` （現在の名簿）や `history`（現在の履歴）から都度ライブに再計算している（`computeUnassignedSummaryHtml()` / `computeOverburdenedSummaryHtml()`）。しかしこれらは、確定後に名簿やルールが変更されると、確定時点とは異なる内容に変わってしまう。「勤務表の作成方法・割当内容・除外対象者などの履歴を残す」という目的に反するため、**確定した瞬間のHTMLをそのまま文字列として凍結保存**し、`genStatus === 'confirmed'` の間はライブ計算をせず、この凍結値をそのまま表示する。

```js
if (locked && (genFrozenUnassignedHtml !== null || genFrozenOverburdenedHtml !== null)) {
  unassignedEl.innerHTML = genFrozenUnassignedHtml || '';
  overEl.innerHTML = genFrozenOverburdenedHtml || '';
} else {
  unassignedEl.innerHTML = computeUnassignedSummaryHtml();
  overEl.innerHTML = computeOverburdenedSummaryHtml();
}
```

確定後に名簿を編集して画面をリロードしても、この凍結値は変わらない（Playwrightのテストで確認済み。9.3節）。

### 6a.6 引き戻し（`confirmBatchId` による選択的な履歴削除と作成履歴ログ）

「引き戻して修正」ボタン（`#gen-revert`、`genStatus === 'confirmed'` の間のみ表示）は以下を行う。

1. `history` から `confirmBatchId` が現在のセッションのものと一致する行だけを取り除く（`history.filter((h) => h.confirmBatchId !== batchId)`）。Excel勤務実績取込や変更届反映等、`confirmBatchId` を持たない他の履歴行には一切影響しない。
2. 引き戻し前の内容（`confirmBatchId` / `confirmedAt` / `revokedAt` / その時点の `dates` / `results`）を `genLog` の末尾に追加する（**引き戻し前の確定内容・作成履歴を保持**するため。削除ではなく別配列への退避）。
3. `genStatus = 'draft'` に戻し、`confirmBatchId` / `confirmedAt` / `genApprovalChecked` / 凍結HTMLをクリアする。`draftDates` / `draftResults` 自体はそのまま残すため、ユーザーは引き戻し前の内容から続けて修正できる。

修正後、再度決裁確認（6a.3節）を経て確定すると、新しい `confirmBatchId` が発行され、`history` に新しい行が追加される。旧い `genLog` のエントリはそのまま残るため、1つの処理期で複数回の「確定→引き戻し→再確定」が起きても、それぞれの確定内容が失われることはない。

`genLog` の各エントリは、勤務表作成タブ下部の「作成履歴」テーブルに確定・引き戻し日時と件数で一覧表示され、行ごとに「CSVで書き出す」ボタンでその回の割当内容（日付・曜日・祝日等・係長級・主事級・状態）を再出力できる。

### 6a.7 プルダウンでの手動調整と「移動」の扱い（`result-select` change）

旧版は、プルダウン（`.result-select`）で職員を選び直すと、選んだ日・欄（`draftResults[idx][level]`）だけを書き換え、`revalidateDraftResult(idx)` もその1行しか呼んでいなかった。そのため、既に別の日に割り当て済みの職員をプルダウンで選ぶと、元の日の割当はそのまま残って二重に割り当てられ、しかも元の日は再判定されないため状態表示が更新されず「OK」のまま見える一方、選び直した日だけに「同一処理期内で2回目の割当です」の要確認が現れる、という不具合があった（利用者からの指摘で発覚）。ドラッグ&ドロップ（`swapDraftResultSlots`）は元々2つのセルを入れ替える実装のため、この問題は起きない。

修正では、選んだ職員が現在 `draftResults` の**他の何箇所に割り当てられているか**を数え、件数に応じて扱いを分ける。

```js
const otherOccurrences = []; // { i, idKey, nameKey } の配列（selectしたidx自身は除く）
// ...draftResults を走査して収集...
if (otherOccurrences.length === 1) {
  // 他の割当がちょうど1箇所だけ：移動とみなしてクリアする
} else {
  // 0箇所、または2箇所以上：クリアはせず、影響する行をすべて再判定するだけにとどめる
}
```

- **他の割当が0箇所**：単純な新規割当。従来どおり。
- **他の割当がちょうど1箇所**：通常の運用（職員数に対して指定日数が極端に多くない限り、同一職員が複数日に入ることは稀）ではこのケースがほとんどであり、「移動」の意図と一致するため、その1箇所を自動的にクリアする。
- **他の割当が2箇所以上**：人数不足で既に複数回割り当てられている職員を、さらに別の日へ選んだケース。どの割当を「元の場所」としてクリアすべきか一意に決められないため、**データは変更せず**、影響するすべての行（新たに選んだ行＋既存の割当がある全ての行）を `revalidateDraftResult()` で再判定するだけにとどめる。これにより、実際に重複している全ての日に正しく「同一処理期内で2回目の割当です」が表示され、少なくとも状態表示が事実と食い違うことはなくなる。

いずれの場合も、影響を受けた行のインデックス集合（`affectedIdxs`）をすべて `revalidateDraftResult()` にかけてから再描画する。

### 6a.8 履歴の一括削除（`initHistoryBulkDelete`）とセッションとの整合性

履歴・確認タブの「表示中の履歴を一括削除」（`#history-bulk-delete-btn`）は、`visibleHistory()`（表示フィルタ適用後の一覧。全期間／未分類／各処理期に対応）が返す配列をそのまま削除対象とする。件数を確認ダイアログで提示したうえで、`history = history.filter((h) => !rows.includes(h))` により参照一致で除去する（日付の一意性に依存しないため、同一日付が複数存在するような異常データでも安全）。

改修（6a章）より前に確定された履歴は `confirmBatchId` を持たないため、この一括削除は6a.4節の確定フローとは無関係に、旧データも新データも同じ経路でまとめて削除できる。ユーザーからの実際の相談（別PCで改修前に確定した疑似データを消したいが、対応する `genSessions` が存在せず「引き戻して修正」が使えない）を受けて追加した。

削除対象に `confirmBatchId` を持つ行が含まれていた場合、その `periodId` の `genSessions` エントリが `status === 'confirmed'` かつ同じ `confirmBatchId` を指していれば、実体のない確定済み表示が残らないよう `status: 'draft'` へ戻し、`confirmBatchId` / `confirmedAt` / `approvalChecked` / 凍結HTMLをクリアする。選択中の処理期が対象に含まれる場合は `loadGenSessionForCurrentPeriod()` を呼び直し、勤務表作成タブの表示もその場で更新する。

## 7. アプリ内ドキュメント表示の設計

### 7.1 目的

仕様書・設計書を、外部の閲覧環境（GitHubやMarkdownビューア）に依存せず、アプリ単体（`file://` を含む）で閲覧できるようにする。

### 7.2 実装方式

`fetch()` は `file://` オリジンで失敗する（OCR機能で確認済みの既存の制約。README「注意事項」参照）。このため、Markdown原本（`docs/仕様書.md` `docs/設計書.md`）をそのまま `fetch` で読み込む方式は採用できない。

代わりに、Markdown本文をビルド時（＝更新のたびに `build_docs.js` を実行した時点）に文字列としてJSファイル（`docs-content.js`）へ埋め込み、`<script>` タグで読み込む方式とする。

```
docs/仕様書.md ─┐
                ├─ build_docs.js ─→ docs-content.js（SPEC_DOC_MD / DESIGN_DOC_MD を定義）
docs/設計書.md ─┘
```

`docs/*.md` が原本（Gitリポジトリ上でそのまま閲覧・レビューできる）で、`docs-content.js` は生成物。Markdownの内容を変更した場合は `node build_docs.js` を再実行して `docs-content.js` を更新する必要がある（README・使い方タブに明記）。

### 7.3 Markdown → HTML 変換

外部ライブラリを追加しない方針のため、本アプリで使用する範囲のMarkdown記法（見出し・表・番号なし/番号付きリスト・強調・インラインコード・コードフェンス・水平線・段落）のみに対応した簡易パーサ `renderMarkdownDoc()`（ui.js）を実装する。以下は対応スコープ外（仕様書・設計書内では使用しない）。

| 未対応の記法 | 備考 |
| --- | --- |
| 画像 | 使用しない |
| 引用（`>`） | 使用しない |
| ネストしたリスト | 仕様書・設計書内では使用しない（`docs/勤務表作成フロー.md` のMermaid図・ネスト構造はアプリ内表示の対象外） |
| リンク | 使用しない（文書内は文字装飾のみ） |

### 7.4 画面構成

「仕様書・設計書」を独立したタブ（`data-tab="docs"` / `panel-docs`）として新設し、タブ内に「仕様書」「設計書」の切替ボタン（`.doc-switch-btn`）を置いて、選択中の文書のみをレンダリングする（両方を常時レンダリングすると長大になるため）。見出し（`##`）から目次を自動生成し、文書冒頭に配置してジャンプできるようにする。

## 8. Excel入出力の設計

### 8.1 共通処理

`readWorkbookFile(file, callback)` が `FileReader` + `XLSX.read`（vendor: SheetJS）でExcelを読み込み、`sheetRows(ws)` が2次元配列に変換する。各取込機能（名簿・育休・産休・勤務実績）はヘッダー行を検索する専用の `parse*Workbook()` を持ち、列名の完全一致ではなく「特定の列名の組が存在する行」をヘッダー行として検出する（人事システムの出力に余分な行が付くことがあるため）。

### 8.2 級・性別・除外の自動判定

`levelFromRank()`（ランクによる級判定）、`suggestLevelForTitle()`（職名による級の推定。ランク不明時のみ使用）、`genderFromValue()`（1/0または男/女の性別判定）、`isExcludedCategory()`（区分名による除外）を独立関数として持つ。判定ロジックの単体テストをしやすくするため、DOM操作から切り離してある。

`parseStaffWorkbook()` は「身分」「年度年齢」列も読み取り、`status`（文字列）・`age`（数値、空欄は `null`）としてそのまま保持する（級・性別判定のような加工は行わない参考情報）。取込対象外になった行は理由付きで `staffXlsxRows` 由来の配列に集約し、`initStaffXlsxImport()` の確定処理で `periodImportExcluded` へ保存する（6.2節・6.4節）。

### 8.3 出力

CSV（`downloadCsv`。UTF-8 BOM付きでExcelでの文字化けを防止）、PDF（`exportRowsToPdf` / `exportPeriodPdfByQuarter`。html2canvasで印刷用HTMLを画像化し、jsPDFへ埋め込み）、引継ぎ用Excel（`XLSX.utils.aoa_to_sheet` で配列から直接ワークシートを組み立て）の3方式を実装している。

### 8.4 PDF出力の四半期ページ分割

印刷用シートの組み立て（`buildPrintSheetEl`）と、1枚のシートを画像化してPDFページへ追加する処理（`addSheetPagesToPdf`）を分離している。列見出しは係長級・主事級の別を出さず、いずれも「氏名」とする。

- `exportRowsToPdf(title, rows, filename)`：全件を1つのシートに描画し、高さがA4に収まらない分だけページを追加する（履歴PDF等、期間を区切らない出力で使用）
- `exportPeriodPdfByQuarter(period, rows, filename)`：処理期の開始日から3ヶ月分・残り3ヶ月分の2つのシートを別々に作り、それぞれ独立したページ（1シートがA4を超える場合はそのシート内でさらにページを追加）として出力する（勤務表作成タブの「PDFで書き出す」で使用）。前期は4〜6月／7〜9月、後期は10〜12月／1〜3月に自然に一致する。該当日がない期間も「該当日はありません」と表示したページとして出力し、常に2ページ構成になるようにしている
- 2つのシートは `Promise` チェーン（`chain = chain.then(() => addSheetPagesToPdf(...))`）で順番に処理する。html2canvasの呼び出しを並列化すると、オフスクリーンに同時配置した複数の `.print-sheet` 要素が競合するため、必ず「描画→画像化→DOMから削除」を1シートずつ完了させてから次に進む

## 9. テスト方針

### 9.1 ロジック単体テスト（Node.js）

`app.js` を `require()` し、実データを模した職員・履歴オブジェクトを渡して `generateAssignments()` の結果を検証する。ビルド工程・ブラウザを介さないため高速に実行できる。本アプリの開発では以下の観点を優先的にテストしている。

- 段階的緩和の各段階が正しい順序で試されるか
- 係長級2名ペアが係長級＋主事級ペアと同じ優先度で選ばれるか（タイブレークの公平性）
- 課長補佐・副主幹の組合せ回避が機能するか、緩和時に正しい理由が付くか
- ペアキーの対称性（anchor/partnerの順序によらずペア重複回避が効くか）
- 同一処理期1人1回ルールの境界（枯渇時のみ2回目を許可するか）
- 既存ルール（120日間隔・年末年始/GW重複・育休産休除外等）の回帰

### 9.2 ブラウザE2Eテスト（Playwright）

`python3 -m http.server` で配信し、Playwright（Chromium）で実際の操作を再現する。`localStorage` へ `addInitScript()` でテストデータを事前投入し、以下を確認する。

- 旧データからの自動移行（IDの引継ぎ・処理期ごとの名簿分離）
- Excel名簿取込の置き換え・引継ぎ・自動判定（実ファイルを介さず、内部変数 `staffXlsxRows` へ直接テストデータを注入し確定処理を検証）
- 勤務表作成タブでのドラッグ&ドロップ（`DragEvent` を手動で発火させて検証。Playwrightの標準ドラッグ操作は本アプリのカスタムD&D実装との相性が悪いため）
- バックアップの新旧フォーマット双方の復元
- 全タブの遷移でコンソールエラーが出ないこと（回帰確認）
- 決裁確認ゲート（チェック前は確定不可）、確定後の編集ロック、確定内容の画面リロード後の保持、「引き戻して修正」による履歴削除と作成履歴ログへの退避、再確定、確定時点のサマリ凍結（引き戻し後の名簿変更・リロードを経ても値が変わらないこと）を実Excelファイル経由の取込を含めて確認（6a章）

### 9.3 テストで見つかった不具合の例

開発中、テストによって以下の不具合を実装前に検出・修正した。

- 2人目プールのタイブレークが係長級に系統的に偏る問題（5.6節）
- ペアキーの非対称性による、係長級2名ペアのペア重複回避漏れ（5.7節）
- 手動変更（プルダウン・ドラッグ）後に、同一処理期内2回目の割当の警告が消えてしまう問題（`revalidateDraftResult()` に1人1回ルールの再判定を追加して解消）
- 移行処理で処理期の `citizenExpNumbers`（旧形式）が新形式の `citizenExp` へ引き継がれていなかった問題
- `mdInline()` が本文中の `<script>` 等のHTMLタグ様の文字列をエスケープせずに `<code>` へ埋め込んでいたため、当該インラインコードの直後からブラウザがraw textモードに入り、文書後半のタグ（コードブロック等）が丸ごとテキストとして飲み込まれ描画が壊れる問題（`mdInline()` の先頭で必ず `escapeHtml()` するよう修正して解消。Playwrightの `querySelectorAll` 件数と生成HTML文字列中のタグ出現数が食い違うという形で発覚した）
