## 1. 「交代を反映」の改修

### 1.1 発見した不具合 ― 「変更する日付」の解釈違い

変更届のテキストを貼り付けて交代を反映する機能に、**出荷済みの不具合**が見つかりました。

変更届の「変更する日付」欄は、実際には**交代相手が日直に入っている日**を指します。
しかし実装では、これを**貼り付けた行の日付**と照合しており、一致しない場合に警告を出すだけでした。

**影響**：この状態で反映すると、交代相手が2日担当になり、申請者はどの日にも入らない状態になり得ます。
しかも担当回数は「公平な回数」の範囲に収まるため、既存のチェックでは検知できませんでした。

### 1.2 対策

| 対策 | 内容 |
| --- | --- |
| 解釈の修正 | 「変更する日付」を**交代相手の担当日**として扱い、「あわせて交換しますか？」に自動で設定する |
| エラー表示 | 交代相手の担当予定が見つからない場合は赤字で警告する |
| 確認ダイアログ | 警告が出たまま「反映する」を押した場合、片道の交代でよいか確認する |
| 最低間隔の判定 | 反映後、その職員の直近の担当日との間隔が `minGapDays` を下回ればポップアップで知らせる |
| 担当回数の判定 | 同一処理期内で「公平な回数」の目安を超えた場合も知らせる |

**最低間隔の判定を足した理由**：上記の二重割当は、必ず「同じ人の担当日が極端に近づく」形で現れます。
担当回数だけでは検知できないため、間隔を見るチェックを併設して安全網にしました。

### 1.3 貼り付け画面の作り直し

「交代相手の行に貼り付けてしまう」取り違えが起きそう、という指摘を受けて、3層で対策しました。

1. **予防** — モーダルの冒頭に「この行の担当者＝変更届の**申請者**」を氏名・日付付きで大きく表示
2. **検知** — 申請者が別人なら**入力欄を一切埋めず**、赤枠で「変更届の申請者」と「この行の担当者」を `≠` で並べて表示
3. **復旧** — 「この行に切り替える」ボタンで、貼り付けたテキストごと正しい行へ移動

赤枠（本当のエラー）と、事前案内の赤字強調は、見た目をはっきり分けています。

### 1.4 「変更届による交代の一覧」

確定済み履歴の下に、反映した交代を新しい順に並べる一覧を追加しました。

- 「日付・氏名・矢印・日付・氏名」の**4分割表示**
- 2人が互いの担当日を入れ替えた場合は**1行にまとめて「←→」**（履歴の丸印と同じ色）
- 片道の交代は「→」で、入れ替え先の日付欄が「―」
- 表示範囲は確定済み履歴の表示フィルタと連動

## 4. 申請手順（申請者向け）

`docs/日直勤務変更_申請手順.pdf`（16:9・7面）

### 経緯

利用者が持っていたNotebookLM製のPDFに「文字化けがある」との相談。調べたところ、
**文字化けではなく、画面写真がAIで描き直された偽物**でした。

| 調査でわかったこと |
| --- |
| PDFに**文字データが1つも無い**（フォント0個・全7ページが画像のみ） |
| ステップ3に**実在しない黒いサイドバー**が描き足されている |
| 日付が実物と違う（`2026年07月05日（日）` / 実物は `2026年10月03日（土）`） |
| 処理者一覧に**実在しない氏名**（「佐藤 遥樹」「久保 千佐」） |
| カテゴリー名の誤り（「稟議／その他」→「異議／その他」ほか） |

### 対応

実物のスクリーンショット6枚を受け取り、**元資料の体裁をそのまま再現**して作り直しました。

- 16:9・7面、見出しと説明文は元資料の文言どおり
- 画面全体を暗転させ、操作箇所だけを明るく浮かび上がらせる方式
- マゼンタのカーソル（ステップ1）、オレンジの矢印・番号・枠（ステップ2〜5）、チェックマーク（ステップ5）
- まとめは青いアイコン5つ＋オレンジの山形

文字はすべてテキストとして入るため、崩れは原理的に起きません。容量は 4.5MB → 1.2MB。

### 一度作り直しすぎた件

最初は独自の体裁（A4横・注意書き多数）に作り変えてしまい、「変わりすぎ」との指摘を受けて
元の体裁に戻しました。**内容の誤りだけを直す**という当初の依頼に沿っていませんでした。

## 5. 検討したが採用しなかったこと

### PDFの容量削減

`docs/日直勤務表アプリ_操作マニュアル.pdf`（3.9MB）を小さくできるか検証しました。

| 方法 | 結果 | 判定 |
| --- | --- | --- |
| PNGを減色（256色） | 3.6MB（−8%） | ✕ 画像単体は62%減るのにPDFは減らない |
| 150dpiに縮小＋減色 | 3.3MB（−17%） | △ 拡大すると粗い |
| JPEGにする | 3.2MB（−17%） | ✕ 画面写真はJPEG向きでなく文字がにじむ |
| **等倍（1倍）で撮り直す** | **2.6MB（−32%）** | ◎ 印刷実寸では区別がつかない |

**わかったこと**：ChromiumはPDFへ埋め込む際に画像を作り直すため、元のPNGを圧縮しても効きません。
効くのは撮影時の倍率（画素数）だけです。

**内訳**：画像2.29MB（59%）／本文の文字1.13MB（29%）／フォント0.28MB（7%）。
本文の文字が大きいのは、Chromiumがフォントを埋め込まず**漢字を1文字ずつ図形として書き出している**ため
（約700オブジェクト）。フォント指定を3通り試しても変わらず、**2.6MBが実質的な下限**です。

**判断**：利用者が「現状のままにする」を選択。3.9MBはメール添付の上限に収まっており、画質は最良のまま。

## 付録D　作業中に踏んだ環境の癖

後続の作業で同じところで詰まらないよう、記録しておきます。

| 事象 | 対処 |
| --- | --- |
| Playwright の `setInputFiles` が**日本語ファイル名を無視する** | 復元用バックアップを ASCII 名で保存 |
| `select.value = x` では `change` が発火しない | `dispatchEvent(new Event('change'))` を明示 |
| `page.screenshot({clip})` は**ビューポートで切れる** | `scrollIntoView({block:'center'})` してから撮る |
| ChromiumはPDF埋め込み時に画像を再エンコードする | 元PNGの最適化は効かない。画素数で調整する |
| poppler が無くPDFを描画できない | zlib と PIL でページ画像を直接取り出して確認 |
| チャットに**貼り付けた画像**はファイルとして保存されない | 添付ファイル（docx等）で受け取り、中の画像を抽出 |
| 作業用フォルダ（scratchpad）はセッションをまたぐと消える | 残すべきものはリポジトリへ（テスト10本を一度失った） |
| `pkill -f "http.server 8899"` が自分のシェルにも一致し、終了コード144になる | `ps aux \| grep "[h]ttp.server 8899"` でPIDを取って `kill` |
